02 / The release event lifecycle

What happens after a CI run reports a deployment candidate.

Primary path
01 · EvidenceGitHub Actions

Install, validate Prisma, lint, run Vitest, build, collect metadata.

02 · SignMetadata collector

Build the event payload and sign timestamp + raw body with HMAC-SHA256.

03 · VerifyWebhook API

Check signature, timestamp freshness, JSON, and Zod contract.

04 · De-duplicateWebhookEvent

Use provider + event ID as the idempotency key in PostgreSQL.

05 · EnqueueInngest event

Dispatch deployment.received and return an accepted response.

06 · ProcessDurable function

Upsert deployment, assemble context, run intelligence, persist assessment.

Important status nuance: the webhook route sets WebhookEvent.processed = true after the Inngest dispatch call succeeds. That marker confirms dispatch acceptance; it is not, by itself, proof that the downstream assessment workflow has completed.
Vercel correlation nuance: the current webhook handler calls the Vercel correlation helper as a best-effort lookup by commit SHA before it sends the Inngest event. If correlation fails, the event can still proceed with the evidence already supplied.

03 / Inside the intelligence engine

The intelligence engine is a staged evaluator. Historical analogies must earn relevance; they are never treated as current telemetry.

01
Build the deployment context

Commit, branch, target environment, changed files, migration clues, runtime, database, infrastructure, feature flags, environment variables, and dependencies.

02
Recall candidate failure experiences

Query the project-specific Hindsight bank for relevant verified engineering memories.

03
Compare historical conditions

Compare runtime, database, pool settings, infrastructure, replicas, flags, variables, and dependencies where data is available.

04
Detect contradictions

Surface opposing mitigations, conflicting root causes, and version-conditional conflicts across recalled memories.

05
Score relevance or abstain

Only memories meeting the default 0.65 floor qualify. Empty or weak recall becomes an explicit abstention, not a fabricated precedent.

06
Evaluate deterministic rules

Apply coded risk rules to current deployment evidence and qualified memories.

07
Explain with Groq + Zod

Groq receives a bounded prompt; its structured JSON is schema-validated. A deterministic fallback exists for mock or failed-provider paths.

08
Enforce the safety floor

A deterministic HIGH or CRITICAL baseline cannot be downgraded by the LLM. Persist the result with its evidence and memory provenance.

0.40 × Hindsight relevance0.35 × failure-signature similarity0.25 × environment match
Interpretation: these weights are an engineering relevance heuristic, not a statistically calibrated probability of deployment failure. A match is context, not proof.

04 / Two stores, two jobs

ReleaseTrace deliberately separates its operational system of record from its historical semantic memory.

Operational source of truth

Neon PostgreSQL + Prisma

Stores the current project, event ledger, deployment facts, assessment results, audit context, and engineer-verified resolution records. The dashboard and deployment pages query this store.

WorkspaceProjectIntegrationWebhookEventDeploymentAssessmentMemoryReferenceResolutionAuditLog
Historical semantic memory

Hindsight Cloud

Stores project-scoped, engineer-confirmed engineering experiences: failure context, confirmed root cause, verified mitigation, outcome, environment, attribution, and evidence.

Project-scoped bankSemantic recallText searchTemporal retrievalGraph retrievalReranking
Never interchange them: Neon answers “what is this deployment and what did we assess?” Hindsight answers “what verified experience may be relevant?” A historical memory cannot replace a current deployment fact.

05 / The memory feedback loop

A memory becomes precedent only after an engineer confirms the root cause and the mitigation. The normal memories API and the separately registered Inngest resolution event are distinct execution paths.

01 · InspectAssessment detail

Engineer reviews evidence, findings, memory references, and the outcome.

02 · ConfirmHuman verification gate

Supply confirmed root cause, applied fix, prevention guidance, and explicit confirmation.

03 · AuthorizePOST /api/memories

Bearer authorization for production writes, or explicitly isolated demo mode.

04 · ValidateSchema + confirmation

Required fields, memory schema, and confirmation.isConfirmed === true.

05 · RetainRetention workflow

Directly invokes retainVerifiedExperience and writes to the project bank.

06 · Recall laterFuture assessment

Qualified memories can inform later releases, with relevance and environment checks.

Production vs demo: a valid bearer token authorizes the production-bank write. Demo mode routes the memory to a separate demo-… project/bank and labels it as synthetic/demo precedent. A shared bearer token is not proof of a uniquely identified engineer.
Separate event function: processVerifiedResolution listens for releasetrace/resolution.confirmed; it can retain a confirmed case and upsert a relational Resolution. That event handler is not the call path used by POST /api/memories.

07 / Trust boundaries & security controls

The trust boundary begins at ingestion and continues through every persistence and memory-write path.

A
Payload authenticity

HMAC-SHA256 verifies the raw request body using the configured webhook secret; timing-safe comparison is used.

B
Replay resistance

Timestamp freshness is checked with a 300-second maximum age; invalid or stale events are rejected.

C
Contract validation

Deployment events and model-generated assessment structures are checked against Zod schemas.

D
Idempotency

A unique provider/event key prevents duplicate processing from creating duplicate deployment records.

E
Project scoping

Server-configured project scope is used for reads; an unauthenticated query parameter cannot select another deployment tenant.

F
Human-confirmed retention

Unconfirmed hypotheses are rejected; production writes require bearer authorization, with demo data isolated.

08 / Product boundaries — what is live, what is a rehearsal, what is not automated

A clear architecture must show boundaries as well as capabilities. These distinctions are part of the product contract.

Live, persisted product paths

Dashboard aggregates; deployment register; real deployment detail; persisted assessments and memory references; Hindsight recall/retention API; integration-health probes when configured.

Direct assessment / fixture path

/api/assess can evaluate a submitted context directly. Its explicit FIXTURE mode returns synthetic fixture data; it is not a production webhook assessment.

Learning and simulation

Learning Lab, glossary, architecture walkthrough, and release simulator are explanatory/rehearsal surfaces. Do not interpret a scenario run as an actual deployment or a persisted production record.

Human-controlled operations

ReleaseTrace does not execute production deploys, rollbacks, canary promotions, or mitigations automatically. Real deployment details are read-only evidence and assessment views.

Optional evidence

The direct assessment schema accepts a telemetry snapshot. The current webhook worker’s context builder does not pass a telemetry snapshot into the intelligence engine; do not assume runtime telemetry is wired into the standard CI event path.

Identity / tenancy scope

The current API uses a server-configured project ID for core reads. A shared bearer credential authorizes memory retention but does not establish a unique per-user identity or a full multi-tenant membership model.

Deployment status reconciliation · open gap

The current Inngest workflow creates a new Deployment with status BUILDING, then persists its assessment. The inspected workflow does not update that row to a terminal Vercel state such as READY or ERROR. The Vercel correlation helper enriches URL/ID, but do not treat the stored status as a verified final provider state until status synchronization is implemented.

10 / CI quality gates

The repository’s primary CI workflow provides build/test evidence and may dispatch a signed event when configured.

npm ciPrisma validateESLintVitestNext buildSigned dispatch

Playwright end-to-end tests are separately exposed through npm run test:e2e; they are not part of the primary workflow by default.

Verification principle: a green CI run proves that the tested revision passed those CI checks. It does not prove that production secrets are present, external providers are reachable, or every browser interaction is connected to live data. Those require separate live probes and an end-to-end signed event test.
